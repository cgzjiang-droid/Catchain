# Slice 7：为何需要评估上下文

旧CATchain从整份PDF取第一处BE/PE/LE/ER，缺少明确周期，随后按关键词评分。
存档参考项目的文件版本思想能帮助追溯来源，但不提供CATchain所需的评分规则或周期判断。
新版把评估上下文独立记录，绑定已批准fact_id、版本、周期、负责人、理由及定位证据。

关键代码：domain/assessment.py定义输入合同；scoring/business_checks.py检查门槛并做算术诊断。
输入是已保存准备度报告和可选人工上下文；输出是阻止原因、逐维检查状态和诊断结果。
整个过程是确定性Workflow，不需要RAG/Agent，也不调用模型。沿用现有Pydantic与Decimal，不加依赖。

例如BE=100、PE=10、LE=5、报告ER=90，且人工确认它们同周期：
诊断复算为85，差异为5。这个数字不能直接变成“得2分”：容差、适用公式与充分证据还未批准。
跨周期则不相减；缺失PE不填0；报告ER为0时误差百分比无定义。

程序能检查UUID、类型、单位、日历日期和原文位置。人工确认这些数值确实属于同周期，
以及文档版本/来源权威。quote存在不证明语义支持，authority_confirmed也不是登录认证。
正式事实变更后旧准备度拒绝执行；重新生成快照保留新旧处理结果，避免旧值参与新评估。

产品验收应询问：同周期有谁确认、证据在哪、复算不一致如何处置、规则版本能否复现。
面试可能问：为什么不让LLM直接打分？事实、计算与业务判定是不同责任，模型输出不能替代可核查输入和审核依据。
当前Task 2技术检查已实现，完整逐维业务规则、官方适用版本及真实人工验收仍未完成。
