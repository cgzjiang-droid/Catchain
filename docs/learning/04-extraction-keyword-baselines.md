# 第四阶段：抽取候选与比较基线

## 2026-09-17：Task 1 已完成

上一阶段得到逐页文字；本阶段先规定抽取结果应该长什么样。
这份共享合同给Regex和后续LLM使用，方便用相同字段比较结果。

`FieldObservation` 是一个候选值，不是最终答案。例如测试里的
`12.5 MW` 保存原始数字 `12.5`、标准化数字 `12.5`、单位 `MW`，以及
文档版本、第一页、原文 `12.5 MW` 和页内位置0–7。位置终点不包含在切片中。

`ProjectExtraction` 把候选值和项目、Parsed结果ID、抽取器版本放在一起。
它检查证据是不是属于这个文档版本。同一个字段可以保留多个不同候选值，
不能让后一个数字直接覆盖前一个。没有支持的规则时使用
`unsupported_by_baseline`，有规则但没找到时使用 `not_found`。

这些规则已经通过运行测试。生成Schema共7份，其中2份是本次新增的抽取合同。
但合同还不能证明原文真的存在、单位正确或日期权威，这些属于Slice 6验证。
人工修改前后值、负责人和裁决记录仍在Slice 8实现。

旧程序的反例也已运行：一段明确否定并网与适用性的文字仍得到关键词满分。
所以关键词评分只能作为baseline，不能称为可靠的项目质量结论。

产品经理此时需要知道：**有输出格式、有候选值、有正确答案是三种不同状态。**
当前已经有输出格式；下一个Task才会从页面产生实际候选值。

验证命令：`venv/bin/python -m pytest tests/unit/domain/test_extraction.py -q`。
下一步：Slice 4 / Task 2，逐页Regex抽取。

## Task 2：基础规则已实际运行

现在已从11份开发PDF生成候选，不仅是一个格式。关键代码是
`src/catchain/extraction/baseline/regex.py` 的extract_regex：输入Parsed页面、
项目ID和registry，逐页正则匹配，输出共享ProjectExtraction。
不同页的容量保留为不同候选，原文不先压缩空格，位置不会被清洗操作改变。

旧实现合并文字后取首值，参考仓库提供文档metadata/hash版本追踪思路，
我们在它们之间增加页级证据。它的设计不能替代碳项目自己的字段规则。
一个候选能精确回到原文，只证明grounding位置可检查，不代表数字语义正确。

选择Regex先行是为了建立可运行比较起点；LLM后续使用同一合同，才能公平
比较。Regex置信度为None，不能伪造80%/95%。缺证据、低置信度与人工裁决
继续由验证和审核Slice处理。

真实输出和局限见 `docs/validation/2026-09-17-slice-4-baselines.md`。
新版交付包还含公司与计入期规则，所以下一步为Task 2B，并非直接跳到LLM。
面试可解释：为什么原值与清洗值分开？两个容量冲突为什么不能覆盖？为什么
旧值和新值一致不等于业务答案正确？

## Task 2B：公司角色、日期与run身份

旧CATchain的标签与计入期规则提供业务输入；参考仓库的hash/version帮助固定
来源。我们在现有共享合同里扩展字段，不增加公司服务或新依赖。
关键代码仍是extract_regex和FieldObservation/ProjectExtraction。

公司分业主、开发方、参与方和运营方。提到SGS不能自动认定它是核查方；
一个标签含多个公司时保留原段，不贸然按and或斜杠拆法律名称。
03/04/2020不猜月日；2027不补为1月1日。所有候选显式unvalidated。
run ID代表哪次处理，文档版本ID代表哪个输入；开发run JSON记录两类Hash，
正式数据库身份链仍需接入。

当前11 PDF未命中标题标签，不等于没有标题或项目无效，说明标签规则覆盖
有限。覆盖率、正确率和可追溯性分别验收。面试可问：日期有歧义为什么不
立即标准化？公司为什么保留角色？run ID和文档版本ID有什么区别？

## 抓取与公司资产审计检查点

真实旧抓取器的三Registry分支已核对，未来adapter只负责发现文档，Hash、
版本和下载失败用共享流程管理。当前新平台联网抓取还没有实现。
GS获取接口403返回空列表会误导成无文档；CSV索引有记录不证明下载成功。
这些失败状态必须分别设计，避免后续缺字段被误判为项目质量差。

旧公司整理把Alpha & Beta Ltd拆成Beta Ltd，说明字符串清洗也可能破坏事实。
新合同保留原值、角色和证据，实体归并另行验证。面试可问：同名文件为何
不能跳过版本检查？失败与缺失有什么区别？相同公司名为何不能直接合并？
下一步Task 3独立关键词baseline，不能称为最终业务评分。

## Task 3：把比较起点与业务评分分开

旧程序按关键词模式是否出现给0–3分，不检查否定语义；现在版本化保留相同
12维规则，输入Parsed页，输出分数与可定位EvidenceRef。high/mid是规则的关键词
等级，不是经校准的概率。一个模式出现很多次，仍只计一次。

GS1003这份6页开发文档得15/36，只说明其关键词命中情况。它不证明项目差，
也不表示事实字段正确率约42%。这就是为什么Extraction和Scoring独立，不能
让抽取器换个实现后把关键词分数提升称为业务质量提升。

关键函数score_keywords逐维读取规则，_first_evidence找首个页内匹配；规则
文件随包安装。参考仓库的版本与来源记录思路在这里体现为baseline版本、
旧源Hash与规则Hash；碳业务维度来自旧CATchain，不来自参考仓库taxonomy。

为什么需要这些代码：后续LLM和最终事实评分需要稳定比较起点；删除baseline
会失去兼容对比，删除证据会让关键词来源不可检查。没有加入评分工厂、新
依赖或LLM判断。最终业务rubric与缺失/冲突处理仍在Slice 7。

面试可能问：为什么关键词很多不是证据充分？重复命中如何计数？如何保证
新版迁移没偷偷改变规则？答案要引用已跑的阈值测试、36项维度对比与真实样本。
下一步Task 4，CLI把导入、解析、候选输出与关键词baseline连起来。

## Task 4：第一次CLI闭环与幂等性

现在可以导入PDF拿到version ID，解析拿到Parsed ID，然后分别抽取和评分。
get_parsed复用已有数据库页面重建逻辑；_run_baseline核对来源身份并调用前面的
extract_regex或score_keywords。store_baseline_artifact固定输入Hash和配置Hash，
把候选与成功run写在同一个文件。重复运行复用原文件，损坏时停止，不默默覆盖。

旧CATchain写JSONL/CSV索引，记录不必然表示成功；参考项目的Hash/版本思想
帮助固定内容身份。我们保留SQLite文档/Parsed存储，先用不可变派生bundle连通
baseline，不提前把未验证值写成Canonical事实，也不增加队列或新数据库。

实际ACR125输出6个匹配字段、49个缺失字段、2个多值候选字段。容量候选的
value可通过document_version_id→Parsed页面→quote/offset回到原文；run则记录
哪次规则处理产生它。JSON可以定位原文，但业务答案仍需Slice 6验证和人工审阅。

当前run记录是成功产物中的JSON，不是完整运行日志表；3份来源URL还是开发
占位，OCR未安装。端到端可运行与可正式上线是不同验收标准。
面试可问：为什么复用结果必须包含规则版本？输入不变但Schema改变怎么办？
为什么损坏结果不能自动覆盖？哪些证据链已经实现、哪些尚未认证？
