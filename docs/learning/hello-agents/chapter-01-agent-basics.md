## 1. 什么是智能体

教材把智能体描述为能够感知环境，并自主采取行动以实现目标的实体。

可以用下面的闭环理解：

```text
目标 → 感知环境 → 决策 → 行动 → 获得新观察
                    ↑              ↓
                    └────继续循环──┘
```

五个判断关键词：

1. 目标；
2. 环境；
3. 感知；
4. 自主决策；
5. 行动与反馈循环。

工具调用是数字智能体常见的行动方式，但不是所有智能体都必须调用软件工具。机器人的行动也可能由电机等物理执行器完成。

## 2. Workflow 与 Agent

CATchain 的固定处理流程是一条由开发者预先规定的路线：

```text
下载 PDF → 解析文本 → LLM 抽取 → 数据验证 → 存储 → 评分
```

即使其中调用了 LLM，只要下一步仍由预先写好的流程决定，它主要还是 Workflow。

Agent 的关键区别是：系统根据新观察和内部状态，自主决定下一步行动。例如，解析失败后选择 OCR，发现字段缺少证据后选择重新检索相关页面，仍无法解决时选择提交人工审核。

## 3. 学习者回答与修正

问题：为什么第二种处理方式比固定流水线更接近 Agent？

学习者回答：

> 第一个是 Workflow，第二个有观察、思考、计划、工具选择，然后执行。

这个判断正确。还需要补充两个判断点：

1. Agent 的行动服务于一个目标，而不是为了调用工具而调用工具；
2. 行动之后会产生新的观察，Agent 根据反馈继续决策，形成闭环。

面试时可以回答：

> Workflow 的步骤和分支主要由开发者预先定义；Agent 则围绕目标感知环境，依据当前观察和状态自主选择行动，并根据行动反馈继续循环。使用 LLM 或调用一次工具本身，并不能证明系统是 Agent。

## 4. CATchain 当前结论

新版 CATchain 的主数据管线目前应被称为 Workflow。它的下载、解析、抽取、验证、存储和评分步骤都有明确边界。未来如果实现“数据质量问题处理 Agent”，它可以观察验证错误，自主选择重新解析、OCR、定向抽取、Registry 查询或人工审核等动作。

这个 Agent 是未来可能加入的异常处理能力，不应为了简历标签替代可靠的主数据管线。

## 5. 使用 PEAS 描述任务环境

Hello-Agents 第一章使用 PEAS 模型描述智能体的任务环境：

- Performance：性能度量；
- Environment：环境；
- Actuators：执行器；
- Sensors：传感器。

以 CATchain 数据质量问题处理 Agent 为例：

- Performance：字段正确、有证据、验证通过，同时控制成本和错误写入；
- Environment：Registry、PDF、页面文本、数据库、验证报告和人工审核队列；
- Actuators：下载器、PDF Parser、OCR、LLM 抽取器、数据库写入和人工审核提交接口；
- Sensors：HTTP 响应、Parser 输出、OCR 置信度、Schema 错误和 Evidence 验证结果。

### PEAS 练习 1

场景：CATchain 下载了一份 PDF，文本解析器返回 0 个字符，于是系统调用 OCR。

学习者最初回答：

```text
Environment：下载的网站
Sensor：文本解析器
Observation：PDF
Actuator：OCR
Action：返回 0 个字符，换 OCR
```

修正后的表达：

```text
Environment：Registry 网站、已经下载的 PDF 以及文档处理环境
Sensor：文本解析器
Observation：解析结果包含 0 个字符
Actuator：OCR 工具
Action：使用 OCR 工具识别这份 PDF
```

关键区别：

- Sensor 是获得信息的渠道，Observation 是这次实际得到的信息；
- Actuator 是执行行动的能力或接口，Action 是这一次具体执行了什么；
- “返回 0 个字符”属于观察，不属于行动；
- “PDF”只是环境中的对象，并不是本次观察结果。

## 下一节

判断固定的 OCR fallback 是 Workflow 还是 Agent，并进一步确定 CATchain 中真正适合 Agent 的业务边界。

### Workflow 判断练习

问题：下面的固定规则是 Workflow 还是 Agent？

```python
if extracted_text_length == 0:
    run_ocr()
```

学习者回答：Workflow。

在现代 LLM 应用和产品简历的语境下，这个回答正确。下一步完全由开发者预先规定，系统没有围绕目标诊断问题、比较多个行动、选择工具并根据反馈调整计划，因此不应该把它包装成 LLM Agent。

需要注意术语语境：按照传统 AI 的宽泛分类，只要一个实体感知环境并按照“条件—动作”规则行动，它也可能被称为简单反射智能体。Hello-Agents 第一章正是从这种传统分类开始介绍。但是在现代 AI 工程语境中，单个固定分支通常更准确地称为规则或 Workflow，而不是大家通常所说的 LLM Agent。

面试时可以这样回答：

> 从传统 AI 的宽泛定义看，它具有简单反射智能体的条件—动作特征；但在现代 LLM 应用工程中，它只是确定性的 OCR fallback Workflow，不具备 LLM 驱动的自主规划、动态工具选择和多轮反馈调整，因此我不会把它包装成 LLM Agent。

## 6. CATchain 的边界判断规则

```text
已知条件 + 预定动作                         → 确定性 Workflow
目标 + 不确定问题 + 动态选择行动 + 反馈循环 → Agent 候选
高风险写入或证据不足                       → 人工审核
```

CATchain 主数据管线继续采用确定性 Workflow。未来真正适合 Agent 的位置是异常调查与修复：当验证失败原因不确定时，系统可以在重新下载、替代 Parser、OCR、定向 LLM 抽取、Registry 查询和人工审核之间选择下一步行动。

## 下一步

学习第一章介绍的简单反射、基于模型、基于目标和基于效用四类智能体，并映射到 CATchain。

### 智能体类型练习

场景：系统在高准确率但高成本的 OCR-A 与低准确率但低成本的 OCR-B 之间，结合文档重要性、预算、准确率和时限动态选择。

学习者选择：D，基于效用的智能体。

理由：系统不只是判断哪个方案能够完成 OCR 目标，还会比较重要性、预算、准确率和处理时限，在多个可行行动中选择综合收益更高的方案。

可以把这个选择抽象为效用函数：

```text
utility(action) =
    accuracy_weight × expected_accuracy
    - cost_weight × expected_cost
    - latency_weight × expected_latency
    - risk_weight × expected_risk
```

这里的公式只是帮助理解，实际权重必须来自业务目标和评估数据，不能由 LLM 随意决定。

## 7. 教材代码 `FirstAgentTest.py` 初步拆解

第一章的配套代码实现了一个旅行助手，主要组成如下：

1. `AGENT_SYSTEM_PROMPT`：告诉模型目标、可用工具和 `Thought/Action` 输出协议；
2. `get_weather` 与 `get_attraction`：两个真实工具；
3. `available_tools`：从工具名映射到 Python 函数；
4. `OpenAICompatibleClient`：调用兼容 OpenAI 接口的 LLM；
5. `prompt_history`：保存用户请求、模型输出和工具 Observation；
6. 最多五轮的 `for` 循环：反复调用 LLM、解析 Action、执行工具并写回 Observation；
7. `Finish[...]`：模型认为信息足够时结束任务。

它之所以比固定旅行 Workflow 更接近 LLM Agent，是因为下一步调用天气工具、景点工具还是结束任务，由 LLM 根据当前历史和 Observation 动态决定。

这份代码为了教学直观，使用正则表达式解析模型生成的文本 Action，而不是真正的 API Structured Tool Calling。它还存在生产工程上的不足，例如文本协议脆弱、缺少 Schema Validation、异常处理较粗、没有成本与 Token 记录。CATchain 应学习它的 Agent Loop，而不是直接复制这套正则解析方式。

### `prompt_history` 练习

学习者选择：B，`prompt_history` 承担当前循环的上下文状态。

如果 Observation 不写入 `prompt_history`，下一轮 LLM 不知道工具已经执行以及返回了什么。它不一定会暂停，更可能重复调用工具、猜测工具结果，或者在信息不足时错误结束。

这里的 `prompt_history` 是一次运行中的短期上下文状态，不等于跨任务长期保存的 Memory。

## 8. CATchain 最小 Agent Loop 实验

对应代码：

- `src/catchain/learning_labs/agent_loop.py`
- `tests/unit/learning_labs/test_agent_loop.py`

实验的数据流：

```text
Goal
  ↓
decide(goal, observations)
  ↓ ToolCall(parse_pdf)
普通解析返回空字符串
  ↓ Observation 写入状态
decide(goal, observations)
  ↓ ToolCall(ocr_pdf)
OCR 返回项目文本
  ↓ Observation 写入状态
decide(goal, observations)
  ↓ Finish
AgentResult
```

代码概念映射：

- `goal`：目标；
- `decide`：决策器；
- `ToolCall`：工具行动；
- `tools`：可用执行器；
- `observations`：工具反馈和当前短期状态；
- `Finish`：结束决定；
- `max_steps`：停止条件；
- `AgentResult`：最终答案、观察历史和执行步数。

当前实验没有调用 LLM。测试中的 `decide` 是确定性的测试替身，因此这个实验只是把 Agent Loop 的编排机制跑通，不能据此宣称 CATchain 已经拥有生产级 LLM Agent。以后可以在不改变循环基本接口的情况下，将 `decide` 替换为经过 Structured Output 验证的 LLM 决策器。

TDD 结果：测试先因 `catchain.learning_labs` 尚不存在而失败；实现最小循环后，专项测试通过，完整测试集为 22 passed，Ruff 检查通过。

### 删除 Observation 回写的实验

暂时删除下面这一行：

```python
observations.append(observation)
```

学习者预测：

1. 决策器没有结果可读；
2. 每轮继续选择 `parse_pdf`；
3. 最后触发 `max_steps`。

实际测试结果与预测一致。`observations` 一直是空元组，因此 `decide` 每轮都进入首次解析分支，循环无法到达 OCR 或 `Finish`，最终抛出 `RuntimeError: agent reached max_steps without finishing`。恢复 Observation 回写后测试重新通过。

这个实验说明：工具执行不等于 Agent 已经获得反馈。只有把工具结果转换成 Observation 并写入下一轮能够读取的状态，才能形成真正的反馈闭环。

## 9. 为什么 Agent 需要 `max_steps`

`max_steps` 是 Agent Loop 的安全边界，不是智能能力。LLM 可能因为工具持续失败、Observation 表达不清或决策错误而一直不返回 `Finish`。如果循环没有上限，就可能产生：

1. 无限循环，任务永远不结束；
2. 重复调用 LLM、OCR 或外部 API，导致成本失控；
3. 长时间占用进程，增加用户等待时间；
4. 重复执行数据库写入、发送请求等有副作用的动作；
5. 频繁访问 Registry，触发限流或封禁；
6. 故障无法及时进入人工审核。

当前学习实验设置 `max_steps=3`，三次决策分别是：

```text
第 1 步：ToolCall(parse_pdf)
第 2 步：ToolCall(ocr_pdf)
第 3 步：Finish
```

所以当前实现把“决定结束”也计算为一步。如果设为 2，两个工具虽然都已运行，但决策器没有第三次机会返回 `Finish`，最后仍会触发步数上限。

生产级 CATchain 不应只有一个步数限制，还需要组合使用：

- 最大 LLM Token；
- 最大费用；
- 总超时时间；
- 最大工具调用次数；
- 单个工具的重试次数；
- 数据库等有副作用动作的幂等保护。

超过限制时也不应只留下普通 `RuntimeError`。正式系统应保存结构化失败原因，例如 `STEP_LIMIT_EXCEEDED`，连同已执行步骤、Observation 和成本一起记录，并根据任务重要性决定失败、重试或转人工审核。

### `max_steps` 理解检查

学习者回答：如果没有 `max_steps`，当 LLM 一直无法返回 `Finish` 时，系统会持续循环，直到 API 费用用光或发生错误。

这个理解正确。还可以补充：循环也可能造成超时、Registry 限流、重复写入以及有副作用工具被重复执行。`max_steps` 的作用是主动终止失控循环，而不是等待外部系统被动报错。

## 10. 第一轮复习：Agent 与 Workflow

学习者最初回答：

> Agent 有思考能力，对于任务有 Thought；Workflow 是一个固定的流程，只会有一个流程。

这个回答抓住了“Agent 能够决策、Workflow 由开发者预先定义”的方向，但需要两点修正：

1. Workflow 不一定只有一条直线。它也可以包含条件分支、循环、并行和重试；关键在于这些路径和选择规则主要由开发者提前规定。
2. Agent 不一定输出自然语言 `Thought`。传统 Agent 可能使用规则、搜索或效用函数决策；现代 LLM Agent 也可以只输出结构化 Action。真正重要的是它依据目标、当前 Observation 和 State 选择行动。

更准确的表达：

> Workflow 根据开发者预先设计的步骤和分支规则执行任务；Agent 则围绕目标感知环境，根据当前 Observation 和 State 动态决定下一步 Action，并利用行动反馈继续调整。自然语言 Thought 是一种实现或展示形式，不是判断 Agent 的必要条件。

### 第二次表述与术语修正

学习者进一步表述：Workflow 可以由程序员提前决定路径，而 Agent 由 Actuator（LLM）根据目标、Prompt History、State 和 Observation 选择下一步。

前半句正确，后半句需要把 LLM 从 `Actuator` 修正为 `Decision Maker` 或 `Policy`：

- LLM：读取目标和当前上下文，决定下一步 Action；
- Actuator / Tool：真正执行动作的接口，例如 OCR、搜索、下载器和数据库；
- Action：本轮具体的工具调用；
- Observation：工具执行后返回的信息；
- State / Context：当前任务状态；`prompt_history` 是教材保存状态的一种具体实现，其中可以包含 Goal、之前的 Action 和 Observation。

数据流：

```text
Goal + State（包含历史 Observation）
                 ↓
        LLM Decision Maker
                 ↓ Action
          Actuator / Tool
                 ↓
             Environment
                 ↓ Observation
          更新 State，进入下一轮
```

Agent 的工具边界仍由程序员设计。所谓自主决策，是 LLM 在允许的工具、权限、预算和停止条件之内选择下一步，而不是可以任意行动。

### 角色对应复习

学习者已正确完成以下对应：

```text
LLM                     = Decision Maker
OCR 工具                = Actuator
ToolCall("ocr_pdf")     = Action
OCR 返回的项目文本       = Observation
observations 元组        = State
```

这组对应说明学习者已经能够区分“谁做决定”“通过什么能力执行”“本轮具体做什么”“环境返回什么”以及“历史信息保存在哪里”。

### PEAS 复习与纠正

场景：CATchain Agent 检查某个碳项目的“项目开始日期”是否正确，可以读取 PDF、查看 Validation 报告、搜索页面、重新抽取或提交人工审核。

学习者的初步理解：

- Performance：读取 PDF 和查看 Validation 报告后返回的结果；
- Environment：相关页面或 PDF；
- Actuator：LLM 抽取或 OCR；
- Sensor：当前碳项目。

纠正：

- Performance 不是工具返回值，而是衡量任务是否做好的标准，例如日期与原文一致、Evidence 有效、Validation 通过且成本未超预算；
- Environment 的页面和 PDF 判断正确，还可以包括 Registry、数据库、Validation 系统和人工审核队列；
- LLM Extractor、OCR、页面搜索和人工审核提交接口可以作为 Actuator。若 LLM 负责决定下一步，它是 Decision Maker；若一个封装好的 LLM 抽取接口被调用来执行字段抽取，它是 Tool / Actuator；
- 当前碳项目是环境中的对象，不是 Sensor。Sensor 是获得信息的渠道，例如 PDF Parser、Validation 结果读取器、Evidence Checker 或数据库查询；
- Sensor 实际返回的内容才是 Observation，例如“项目开始日期缺少 Evidence”。

完整示例：

```text
Performance：开始日期正确、有原文证据、验证通过、成本未超预算
Environment：项目 PDF、Registry、数据库、验证系统、人工审核队列
Actuator：页面搜索、OCR、LLM 定向抽取、提交人工审核
Sensor：PDF Parser、Validation 报告读取器、Evidence Checker、数据库查询
Observation：Validation 返回 project_start_date 缺少 Evidence
```

## 12. CATchain 人工审核闭环设计练习

### 非空 OCR 结果不等于可用结果

当前学习代码只要 OCR 返回非空文本就执行 `Finish`，因此乱码、错误日期或无法定位证据的文本也可能被当成成功结果。产品层必须先定义“可用”的质量门槛，再让 Codex 实现。

学习者的判断：日期模糊或无法定位原文时，不让系统猜测，应标记为待确认并转人工审核。这个方向正确。

MVP 可以使用文件夹组织待审核文件，但正式的数据模型更适合创建一条审核任务。不要为不同原因复制两份 PDF；同一任务可以具有多个原因标签：

```text
LOW_CONFIDENCE       OCR 或抽取结果置信度不足
EVIDENCE_NOT_FOUND   无法定位支持字段值的原文证据
```

一条最小审核任务应保存：

- 原始 PDF；
- 系统提取的候选值；
- OCR 或抽取置信度；
- 进入人工审核的原因标签；
- 原文页码和证据片段；
- 当前审核状态。

### 审核页面与可追溯性

学习者最初提出审核员需要看到置信度、原因和状态。这些信息能解释“为什么需要审核”，但不足以判断结果是否正确。审核员还必须同时看到候选结果和原始证据；若系统不能定位相关页面，则需要提供整份 PDF 的搜索和翻页能力。

人工确认后需要保存：

- 审核人和审核时间，用于责任追踪和 Audit Trail；
- 来源文档、页码和原文片段，用于 Provenance；
- 修改前的候选值、修改后的确认值和修改原因，用于版本追踪。

历史值不应与正式值混用。系统只能有一个当前正式值，旧候选值进入不可随意修改的审计记录。

### 人工提交后仍需确定性验证

学习者正确判断：人工修改不能直接写入正式数据库，还要检查日期格式、证据和必填信息。可由 Workflow 稳定执行的检查包括：

- 字段格式是否合法；
- 必填字段是否完整；
- 证据文件和页码是否存在；
- 审核人是否存在；
- 开始日期是否晚于结束日期等业务一致性规则。

学习者也正确判断：提交验证失败时应保留草稿、标出具体错误位置并允许修改后重新提交，不能清空已填写内容。这可以减少重复劳动和人工审核时间。

完整闭环：

```text
LLM / OCR 提取
→ 自动质量检查
→ 不合格则创建人工审核任务
→ 人工修改并添加证据
→ 再次执行确定性验证
→ 写入正式数据库
→ 保存完整审计记录
```

## 13. 阈值、评估与上线判断

### 暴露的问题 1：不能根据上一组单个样本移动阈值

学习者认为固定的 80% 可能太死，并提出参考上一组 78% 的样本设置 78% 至 80% 区间。区间设计可以考虑，但不能根据单个或上一组样本直接调整阈值，否则会造成阈值漂移。

正确做法是先使用有人工正确答案的代表性样本，统计不同置信度区间的真实正确率。还要注意：LLM 自报的置信度不一定经过校准，不能作为唯一门禁。OCR 分数、字段格式、原文证据和跨来源一致性都应参与判断。

需要收集的核心数据：

- 系统置信度和人工最终答案；
- 各置信度区间的真实正确率；
- 错误记录被自动放行的比例；
- 转人工数量和平均审核时间；
- 错误类型、文档来源和 PDF 类型。

### 暴露的问题 2：正确率达标后，30% 覆盖率不代表不能上线

学习者最初认为只有 30% 的文件能自动处理，因此仍不应上线。这个判断缺少业务价值计算。如果自动通过记录的实际正确率达到业务要求，30% 的覆盖率仍可能节省大量人工时间，可以先对符合条件的文件小范围上线，其余 70% 继续人工审核。

上线决策需要同时观察：

```text
Precision：自动通过记录中有多少真正正确
Coverage：全部文件中有多少能够自动通过
Review Cost：剩余人工审核需要多少时间和成本
Business Value：自动化实际节省多少时间和费用
```

例如每月有 10,000 份文件，每份人工审核 5 分钟，30% 自动通过可以节省约 250 小时。是否上线应结合风险、节省价值和监控能力判断，不能只看覆盖率百分比。

### 暴露的问题 3：文件数量大与单份文件过长是两个问题

学习者提出 30% 覆盖率可能是 LLM 处理大规模文件时过载，需要分流。这里需要区分：

- 文件数量多影响吞吐量、并发、排队、API 限流和费用，可通过分批、队列和限流处理；
- 单份文件过长可能超过上下文窗口或造成内容遗漏，需要分页、分块、定向检索或分段抽取。

分流可以缓解处理压力，但不必然提高自动通过覆盖率。要提高覆盖率，需要对未通过的 70% 按 OCR 质量、版式复杂度、证据缺失、抽取错误和验证失败等原因分组分析。

当前阶段的关键产品结论：先保证自动通过集合达到业务正确率要求，再依据覆盖率、审核成本和业务价值决定小范围上线范围；上线后持续监控真实错误率，不能只依赖离线置信度。

## 14. 影子测试与灰度上线

学习者已能复述第一阶段上线方案：先进行影子测试，系统结果不进入正式业务结果，只用于评估正确率；再设置置信度、证据可定位和格式验证等准入条件；之后从小比例灰度上线开始，表现达标后逐步扩大；若线上正确率低于要求、证据缺失或连续出现严重错误，则暂停自动通过。

需要补充两个产品细节：

1. 影子测试中，系统输出可以保存到独立的实验结果表，不能覆盖正式值。人工审核仍然产生正式答案，系统结果与人工答案进行对照。
2. “回调”应修正为“回滚”或“降级”。发生停止条件时，通常先把自动通过降级为全部转人工；是否回滚已写入的数据，需要根据错误影响范围另行调查，不能直接批量撤销。

测试样本也要分成两个用途：

- 准入样本：满足高置信度、有证据、验证通过等条件，用于判断可自动通过集合是否达到 99% 正确率；
- 诊断样本：包含未达到准入条件的文件，用于分析剩余文件为什么失败，以及未来如何提高 Coverage。

灰度比例不必机械地固定为 5%、10%、30%。每次扩大范围前都要满足预先规定的样本量、正确率、严重错误数和人工审核反馈条件。

## 15. 影子测试中的正式答案与 Gold Standard

学习者判断：影子测试中系统答案与人工答案不一致时，应以人工答案作为正式结果，因为人工效率较慢，但正确率通常更稳定。这个判断适合作为 MVP 的业务默认规则：系统输出只用于实验对比，不能覆盖人工确认的正式值。

需要修正的是：人工答案也可能出现误读、录入错误或审核标准不一致，因此不能未经验证就把每一个人工答案都视为绝对真相。用于计算模型正确率的评估答案称为 `Gold Standard` 或金标准答案，它应由清晰的审核规则产生。

建议的 MVP 规则：

```text
系统答案 = 实验预测
人工审核答案 = 默认正式业务值
系统与人工不一致或属于高风险字段 = 第二位审核员复核
仍有分歧 = 交给领域专家裁决
最终裁决结果 = 评估使用的 Gold Standard
```

这一区分避免把“人工处理”简单等同于“百分之百正确”，也能防止错误标签让模型评估结果失真。

## 16. 两名审核员意见不一致时的裁决流程

学习者提出：先到已有结果集中查找相同情况的正确日期并进行对比；如果仍不能确定，就放入单独的待观察列表，等待系统给出答案或之后再次人工审核。

其中“查历史结果”可以作为辅助步骤，但必须限制使用范围：只有确认是同一项目、同一文档版本或可信的权威来源时，历史值才可以作为证据。其他相似项目的日期不能证明当前项目的日期正确。系统或 LLM 给出的新答案也不能自行结束争议。

更准确的产品状态不是普通“待观察”，而是 `DISPUTED_PENDING_ADJUDICATION`（争议待裁决）。建议流程：

```text
审核员 A 与审核员 B 给出不同答案
→ 冻结正式值，不自动入库
→ 核对是否为同一文档版本、文件 Hash 和权威来源
→ 展示两人的答案、证据页和原文片段
→ 第三位高级审核员或领域专家裁决
→ 保存裁决答案、理由、证据和全部历史意见
→ 将最终结果设为 Gold Standard
```

如果证据仍不足，任务应保持 `UNRESOLVED`，正式字段标记为未知或待确认，而不是要求系统猜出一个日期。后续获得新文档或新证据时再重新打开任务。

### 这是不是官方步骤

这不是所有 Agent 产品都必须遵守的统一官方流程，也不是 Hello-Agents 教材规定的固定步骤。它属于常见的争议裁决与数据治理设计，具体角色和审核层级需要由组织根据字段风险、业务成本和人员配置决定。

CATchain 当前产品规格已经要求：不确定或冲突结果进入人工审核；审核台支持接受、纠正、拒绝、升级、查看证据和审计历史。但规格尚未规定“第三位小组组长必须裁决”。因此，小组组长作为高级审核员是本轮学习中提出的 MVP 角色方案，后续需要写入正式产品需求并定义权限后，才会成为 CATchain 的正式流程。

措辞上应使用“暂不更新或冻结正式值”，而不是“冻结真实值”。发生争议正说明真实答案尚未确认。裁决完成后，需要保存两位审核员的答案、各自证据、组长的最终决定、裁决理由、时间和人员身份。

## 17. 新旧文档版本出现不同字段值

学习者判断：同一项目出现新版 PDF 后，不能直接沿用旧版人工审核答案；新版应重新执行完整审核，因为它可能代表当前阶段的权威信息。重新审核的判断正确。

需要修正的是：`最新版本` 不自动等于 `正确且权威`。系统还要核对新版是否来自官方 Registry、文档版本号、发布日期、文件 Hash、适用范围，以及它是正式修订版、补充文件还是误上传文件。

推荐的数据处理规则：

```text
下载新版 PDF
→ 建立新的文档版本记录，不覆盖旧文件
→ 重新解析、抽取、验证和定位证据
→ 比较新旧字段差异
→ 判断新版是否为可信且当前有效的权威来源
→ 通过审核后，将新版值设为当前正式值
→ 保留旧值及其有效时间、证据和审核记录
```

如果新旧版本冲突且新版的权威性或适用时间无法确认，应进入争议待裁决流程，不能因为文件时间更新就自动覆盖正式值。
