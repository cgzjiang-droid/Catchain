# 第6课：候选验证与正式事实的边界

旧CATchain输出字段后主要靠格式/关键词完成评分，最终字段与证据之间的链路不完整。
参考归档项目帮助保留来源、版本与文件指纹；CATchain需要自己建立字段验证与审核边界。

关键代码是validation/extraction.py。输入数据库Parsed和共享ProjectExtraction，
输出每条候选的检查结果；不会改写原值。domain/validation.py用Pydantic定义报告合同，
通过检查的JSON也不能擅自把canonical_writes改为非0。

输入质量有不同层次：Schema检查类型形状；Evidence检查原页码和原文位置；
日期/单位检查可执行的数据合同；语义审核检查原文是否支持值和公司角色。
前三层检查结束，不意味着第四层已完成。引用写12MW、候选写99MW时，引用存在也不足以
支持候选，当前系统会要求语义审核，没有自动正式入库通道。

没有置信度时保留未知，不编造概率；0.8目前只是已讨论的分流阈值。高于阈值也不
替代证据或语义规则。未明确的业务字段类型返回待定义，避免把bool/table/text关系猜死。

这一步仍是Workflow，和Hello-Agents的LLM不确定性、数据验证概念对应，不需要Agent。
产品经理应验收：错误位置可见、原候选保留、双方冲突不自动选第一项、格式失败不丢草稿。
面试可问：“验证run成功为什么还有rejected？”run成功表示程序完成了检查，rejected
表示候选发现错误，两个状态描述不同对象。

当前Task 1完成。后续Task 2补字段化/跨字段/跨文档业务规则，Task 3建正式事实数据库，
Task 4接审核裁决输入。审核台UI在Slice 8；目前没有人工裁决记录或Gold准确率。
