# Slice 6 Task 3：候选和正式事实为何分开

当前解决的是存储边界。旧CATchain把抽取和评分结果写为JSON/CSV；这些文件适合交换，
但不适合维护多人审核与多版本候选。参考存档项目的独立来源元数据和版本思想，
CATchain用已有SQLite增加事实处理层，不增加数据库服务器或Agent框架。

关键代码是storage/database.py的6张表、storage/fact_repository.py的import_validation，
以及migrations/versions/0003_fact_candidates.py的冻结迁移定义。
输入是原抽取、抽取run、验证报告和验证run。输出是可复用的事务记录。
报告JSON保留完整原值/原文和提取方法；候选和证据独立表支持关系查询，避免只存一个大JSON。

事务意味着：如果第2条证据存储失败，前面的候选也不应留下半成品。
外键意味着：证据必须引用存在的候选和文档版本。
幂等性意味着：同一报告再导入一次不产生重复数据；同一ID换了内容会报冲突。

作为产品经理，验收重点是“原值是否保留、证据是否可定位、失败是否回滚、候选是否会被误当正式值”。
本步没有模型调用，也没有正式事实写入；裁决表和事实表只是为下一步提供存储边界。
SQL与数据库事务属于数据工程知识，不需要你独立编写数据库实现。

面试可能问：为什么不用Excel？答：Excel仍可导出，但多人审核和版本追溯需要稳定ID、关联约束和事务。
为什么不是PostgreSQL？答：当前单机MVP规模与并发尚未证明需要服务器，SQLite足够验证业务闭环。
为什么不能直接入正式事实？答：存在引用与格式通过不能保证语义正确，需要明确审核决策与证据。
