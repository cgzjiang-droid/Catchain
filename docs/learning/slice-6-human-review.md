# Slice 6 Task 4：谁有权把候选变成事实

旧CATchain的文件输出没有完整人工裁决链；存档参考项目侧重文档版本，不能替代业务审核。
本步由我们实现普通Workflow的人工节点，继续使用Pydantic、SQLite及CLI，无新Agent或依赖。

关键代码：domain/review.py定义输入合同，storage/review_repository.py的decide执行检查与原子提交。
输入包含candidate_id、审核人、理由、状态、看到的当前正式值ID；批准还要提供after和权威确认。
输出为decision_id、fact_id及本次正式写入数。不是LLM直接给总分，也不让置信度替代审核。

三种裁决：approved明确批准；rejected拒绝候选；unresolved证据不足或权威不清。
后两种保留已有正式值。修改后追加新事实，旧事实不删除；完整原候选、修改证据和前后正式值可追溯。
expected_current_fact_id是审核员的“我看到的版本”：如果别人已经修改过，当前提交转草稿，避免覆盖。

程序检查原文位置、日期格式、单位和类型；不保证引用语义正确。
manual-reviewed-v1要求操作员显式确认语义及权威。reviewer目前只是本机输入声明，未实现登录认证。
真实试跑仅记录unresolved路径，批准测试使用构造样例，不能声称真实业务数据已获人工认可。

产品验收：无证据不能批准、未知不能硬选、失败无半成品、重复无重复写入、旧提交不覆盖新值。
面试可能问：组长也无法裁决怎么办？保留unresolved、各候选和理由，待新证据出现重新处理。
面试可能问：有引用为何不能自动批准？引用存在是程序条件，引用是否支持结论是语义与权威条件。
